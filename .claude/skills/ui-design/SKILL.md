# UI 設計の手順

見た目は**コードを読んでも分からない**。描画して、見て、直す。これを省いた UI は完成扱いにしない
（Stop フックが実際に止める）。

## 0. 基準を読む（毎回・省略不可）

1. `design/PRODUCT.md` — 誰が、どんな状況で使うか。こうはしたくない例
2. `design/DESIGN.md` — 方向性と、トークンの使い分けの**理由**
3. `design/tokens.css` — 使える値はここにあるものが全て
4. `design/DECISIONS.md` — 過去に人間から受けた指摘
5. `design/briefs/<画面>.md` と `design/references/`（画像は Read で開く）— あれば

PRODUCT.md / DESIGN.md が無い、または自分のプロダクトと無関係なサンプルのままなら、**推測で進めず**
ユーザーに `/design-init` の実行を提案する。画面ブリーフが無く優先順位が読み取れないときは、
「この画面で一番大事な 1 つは何か」「実データの最長・最多・0 件はどんな姿か」だけ質問する。

## 1. 計画を書く（コードより先に、ユーザーに見える形で）

- **主役**: 3 秒で伝わるべき 1 つ。それ以外は主役より弱くする
- **優先順位**: 情報を 1 位から並べる。同率は作らない
- **ワイヤー**: ASCII で 1 案。デスクトップとモバイル（390px）で何が変わるか
- **使うトークン**: 文字サイズは何段使うか（4 段まで）、色は何系統か
- **状態**: 空 / 最長 / 最多 / エラー をどう見せるか
- **自己点検**: この計画は「どんなプロダクトでも同じになる案」ではないか。
  [references/anti-patterns.md](references/anti-patterns.md) を読み、該当があれば理由を付けて直す

## 2. 実装

- 値は必ず `var(--…)`。無い値が欲しくなったら、近いトークンで済ませるか、ユーザーにトークン追加を提案する
  （`design/tokens.css` は人間の所有物。勝手に足さない）
- セマンティックな HTML を先に書く（`table` `button` `nav` `h1`…）。見た目は後
- 実データの姿で組む。短いきれいなダミーだけで組まない（最長の名前、0 件、桁の多い数字を必ず入れる）
- 和文を含むなら [references/japanese.md](references/japanese.md)
- 編集のたびに design-lint が走る。error は直す。正当な例外は理由付きで抑制する

## 3. 描画して見る

```bash
node tools/ui-shot.js <画面の .html か URL>
```

- 状態違いも同時に撮る: `node tools/ui-shot.js src/x/index.html "src/x/index.html?empty=1"`
  （空・エラーなどの状態は URL のクエリで切り替えられるように作っておく）
- 出力された PNG を **全部 Read で開く**（モバイル / タブレット / デスクトップ / ダーク。ページ全体が写る）
- 描画監査の error は直す。誤検知なら `--ack "<理由>"`

## 4. 批評して直す（最低 1 往復、最大 3 往復）

スクリーンショットを見ながら [references/critique.md](references/critique.md) の観点で自分の画面を批評する。
「問題なし」で終えない — **必ず弱い点を 3 つ挙げ**、直すか、直さない理由を書く。
直したら再度 `ui-shot`。最後に「1 つ取り除けるものはないか」を確認する。

第三者の目が欲しいとき・大きな画面のときは `/ui-review <対象>` を使う（作った文脈を知らない別コンテキストで批評する）。

## 5. 報告

- 何を主役にし、何を弱めたか（1〜2 文）
- スクリーンショットのパス
- 残っている懸念、`--ack` / `--skip` / lint 抑制をしたならその理由
- ユーザーに判断してほしい点（トークン追加の提案など）

ユーザーから見た目の指摘を受けたら、直すだけでなく `design/DECISIONS.md` に 1 行追記する。
